# The web app (M8)

A single page that searches the I₂ B–X line list, plots the spectrum and shows a line's hyperfine
structure. It is static: no server, no WASM, no Schrödinger equation in the browser.

```
web/index.html      the explorer: markup and its styling
web/app.js          the interface: search, plot, table, detail pane
web/physics.js      the physics the browser still has to do
web/site.css        the explorer's colour tokens and navigation
mkdocs.yml, documentation/   the documentation (MkDocs Material): how it works, references, usage;
                    built into the site's docs/ folder. documentation/hooks.py writes the references
                    page from the data at build time; documentation/figures/make_figures.py draws the
                    figures as SVGs coloured by CSS variables, inlined so they follow the theme
web/test_physics.mjs   checks physics.js against the Python model and against the exported data
web/reference.json  Python reference values for that test (web/make_reference.py regenerates them)
web/data/           generated by `i2spec web export` (src/i2spec/webapp.py); not committed
```

```sh
uv run i2spec web                  # build site/ (explorer + docs) and serve it at http://localhost:8777
uv run i2spec web export           # re-export after a model change
uv run i2spec web build site       # the static site, as GitHub Pages publishes it
uv run mkdocs serve                # the documentation alone, reloading as you edit
```

`.github/workflows/pages.yml` runs the build and the physics check on every push to `main` and
publishes `site/` to GitHub Pages; the line lists are cached between runs.

## Why the model is exported rather than ported

The obvious design is to compile the forward model to WebAssembly. That is still the plan for the
Rust core (M7), but it is the wrong thing to build *first*: the model is not frozen, and a WASM port
would have to be rewritten with every change to the potentials or the hyperfine Hamiltonian.

What the browser actually needs per line is a position, a lower-state energy and a
temperature-independent strength. Those are the output of the solver, not the solver itself. So
`i2spec web export` runs the real model once and writes the answer; the app reads it. **Regenerating
`web/data/` is how the app picks up a new model — no part of the app changes when the model does.**
The one thing that would change the app is a new *kind* of output (say, per-line fitted covariance),
not a new value of an existing one.

The cost is what cannot be varied in the browser: the isotopologue, the cutoff strength and the
hyperfine coverage are fixed at export time. Temperature is not — everything that depends on it is
recomputed live, which is why the export stores `s0` rather than `S(300 K)`.

## What the export contains

`i2spec web export` (`webapp.export(s_min=1e-24, n_shards=64, n_hfs=1500)`) writes, per isotopologue:

| File | Contents |
|---|---|
| `lines/<iso>/NNN.json` | a wavenumber slice of the line list: `nu`, `s0`, `el`, `vu`, `vl`, `j`, `m`, `ms` |
| `partition_<iso>.json` | `g[J]` (nuclear-spin weight) and `levels[J]` (X term values), enough to recompute Q(T) |
| `hfs_<iso>.json` | hyperfine components, keyed `"<v'>-<v''><branch><J''>"`, as offsets `o`, strengths `s` and labels `l` |

plus one `manifest.json` carrying the model provenance, the physical constants, the strength cutoff
and the thresholds behind the per-line uncertainty, and one `references.json` listing every
measurement source (precision sets from `data/observations/`, the three assigned FTS atlases from
`data/atlas_lines/`) with its citation, DOI or document link, and coverage.

Conventions that the app depends on:
- **`j` carries the branch in its sign**: positive is R, negative is P. One array instead of two.
- **`s0 = S(300 K) · Q(300 K) · exp(+c₂E″/300)`**, so that `S(T) = s0 · exp(−c₂E″/T) / Q(T)` exactly.
- **`m` lists the rows of that shard we hold a measurement for, and `ms` what those measurements
  are**: per row, one entry per source, `{s: index into references.json, f: [[component, value MHz,
  u MHz, obs − model MHz], ...], i: number of hyperfine intervals}`. Atlas values are hyperfine-free
  centres on the atlas's own scale (Orsay's corrected by its fitted +23.85 ppb); the residual is
  against the model at export time.
- **Every measured line is exported**, however weak: the cutoff applies to unmeasured lines only.
  Measured lines with no absorption at any cell temperature (the v″ = 48–54 emission lines near
  9 400 cm⁻¹) are added with zero strength, so they are listed and marked but draw nothing.
- Lines measured with hyperfine resolution always get a hyperfine pattern, on top of the strongest
  1500 and the strongest 80 of each shard.
- Rounding: ν to 10⁻⁶ cm⁻¹ (0.03 MHz), `s0` to four significant digits, hyperfine offsets to 1 kHz.
  Weak components whose strength rounds to zero are dropped unless they carry a label; that is more
  than half of them, and none of them is visible in any spectrum.

Sharding is by wavenumber so that a search fetches only the slices it overlaps. A 0.1 nm window at
532 nm is one 160 KB file. Searching by line label is the exception: it needs the whole list for that
isotopologue (about 12 MB), so it loads every shard once, with progress in the status bar.

## What the browser still computes

`physics.js`, and only that file:

- the air/vacuum conversion (Edlén 1966) and the five units;
- Q(T) from the shipped X levels, and S(T) from `s0`;
- the Doppler width, the I₂ vapour pressure over the solid (Tellinghuisen 2011 eq. 8) and the
  resulting cell transmission.

The per-line uncertainty is *not* recomputed in the browser. It used to be — a JavaScript copy of the
rules, which drifted: it still described the 2008 potentials ("v″ > 17: no data, 250 GHz") after the
model had gained the MLR curves and the atlas-measured X levels. Now the export evaluates
`lookup.uncertainty` for every line, the same function the CLI and TUI use, and ships the value (`u`,
three significant figures) and an index `w` into `manifest.reasons`, which holds each distinct reason
with its flags.

`node web/test_physics.mjs` checks every one of these against values produced by the Python model,
checks that the exported uncertainties match `lookup.uncertainty` for a few measured lines, and checks
the exported data for self-consistency. Agreement is 10⁻¹² for the closed-form quantities,
10⁻⁶ for Q(T) and 10⁻⁴ for strengths, the last limited by the four-digit rounding of `s0`.

## Interaction

The plot behaves the way a spectrum viewer should rather than the way a map does:

- **drag** pans: the spectrum follows the pointer;
- **shift-drag** selects a range on the axis and zooms to it, with the span shown live above the
  selection in whatever unit is displayed;
- **scroll** zooms about the cursor; a sideways scroll (trackpad, tilt wheel) pans;
- **← →** and **`[` `]`** pan by a quarter view;
- **click** picks the nearest line;
- **arrow keys** walk the results list and carry the selection with them, so the detail pane and the
  marker on the spectrum follow; PageUp/PageDown move ten rows, Home/End jump to the ends. Pressing
  an arrow from anywhere on the page enters the list rather than scrolling it;
- **"all"** in the jump-to row shows the whole exported range at once — 501–910 nm (plus the few emission
  lines measured near 1 070 nm, at zero strength) and about 270 000 lines of ¹²⁷I₂, roughly 20 MB of
  line data the first time and cached thereafter.

Zooming is clamped to the range the export covers, and clamping *widens* rather than slides: an
earlier version truncated the high edge only, so zooming out past the limit looked like a pan.

A drag shorter than four pixels is treated as a click, so selecting a line never accidentally pans.

The spectrum has two horizontal axes, the chosen unit below and wavenumber above (vacuum wavelength
above when the chosen unit is wavenumber), each with round tick values (1, 2 or 5 × 10ⁿ); a label that
would overlap its neighbour is left out. The **show** control is three independent toggles, one per
kind of line.

On a touch screen: one finger pans (the spectrum follows the finger), two fingers pinch-zoom about
their midpoint, and a tap that has not moved more than six pixels selects the nearest line. Each gesture
is computed from the view it started with and goes through the same coalesced view requests as the
wheel, so the spectrum stays under the fingers even when a redraw lags. Lifting one finger of a pinch
continues as a pan from where the other finger is.

## Colour

Iceland: glacial meltwater and black basalt in daylight, basalt and the aurora at night. Colour
encodes two things only — how a line is known (precision, atlas, model only) and which line is
selected — so those colours are validated rather than chosen by eye
(`dataviz/scripts/validate_palette.js`):

| mode | atlas | precision | selection | model only | worst CVD separation |
|---|---|---|---|---|---|
| light | glacier blue `#0070a0` | amber `#b87400` | crimson `#c0306a` | slate `#8a9ba5` | ΔE 10.0 (protan) |
| dark | sky `#3a98cc` | amber `#bd8a1c` | rose `#d9588a` | slate `#6f8590` | ΔE 11.5 (deutan) |

The three hues are checked together (`--pairs all`); the model-only grey is deliberately
achromatic, since it is the unmeasured background the measured lines stand out from. The selection
used to be rust, which is too close to the precision amber.

The dark palette is its own set, lighter and less saturated for the dark ground, not the light one
inverted. Every text colour clears 4.5:1 against both its surfaces.

## Measured lines

Every line has one of three kinds, and each kind has a colour:

- **precision** — measured in a sub-Doppler or comb-referenced data set (`data/observations/`);
- **atlas** — measured only as a Doppler-limited centre in one of the FTS atlases;
- **model only** — not measured; its position is the model's interpolation (or extrapolation).

A line in both kinds of source counts as precision for its colour. In cross-section mode the
spectrum is drawn as stacked fills, precision, then atlas, then model only from the baseline, so the
share of the absorption each kind accounts for is visible at any zoom. The total is outlined on top,
and a legend at the top left counts each kind in view. Measured lines also get a diamond in the strip
under the trace, in their kind's colour. In the table, each row carries its kind as a bar on its
left edge, and the "measured by" column links each source to its DOI (or, for the BIPM documents and
the Orsay atlas, the document itself).

**Show** (all, measured, precision, atlas) filters the spectrum and the table together. "Atlas"
means measured by an atlas, so it includes lines that are also precision-measured. The filter is in
the URL.

The detail pane lists every measurement of the selected line: source, component, published value,
uncertainty and the residual against the model at export time. The references page
(`references.html`) lists the sources with their coverage.

## The table runs along the spectrum

The table is ordered by wavelength, shortest at the top. In that order it continues past its ends:
scrolling on past the last row (or pressing ↓ on it, or clicking the "longer wavelengths" row) moves
the window to longer wavelengths, and past the first row to shorter ones. The new window starts at
the row that was at the edge of the visible table, and the table is scrolled so that row stays where
it was, so the list reads as one continuous list. The move is at least a quarter of the window, and
the window keeps its width. It stops at the ends of the exported range. Any other sort order turns
this off, since "past the end" means nothing there.

## Deliberate limits

- **No sub-Doppler.** Lamb dips and crossovers need the (I, F) labels of the shared levels, which are
  not exported. The TUI has it (`docs/research/sub-doppler.md`); the app does not.
- **No continuum.** The plot is the bound–bound line list only, so it understates the absorption
  below about 500 nm. `i2spec.continuum` has it.
- **No blends across isotopologues.** One isotopologue is plotted at a time, as in the TUI.
- **A wide view costs a fetch.** Showing the whole range pulls every shard for that isotopologue,
  about 20 MB, once.

## Hyperfine structure and pixel averaging

Every line has a ΔJ = 0 hyperfine pattern (main components, offsets to 0.1 MHz, strengths per mille),
written per shard to `hfs/<iso>/NNN.json` with one pattern per row of the matching line file. They are
computed in parallel at export: 1.8 ms per line against 38 ms with the J ± 2 couplings, which change
the offsets by under 1 MHz. Below a 0.1 nm view the app loads the files for the shards in view and draws
each component with the line's Doppler width, plus a stick at each component's own peak height. The
detail pane uses the full (ΔJ = ±2) patterns of `hfs_<iso>.json` where they exist and falls back to the
ΔJ = 0 pattern otherwise.

Lines used to be drawn by sampling their Gaussian at pixel centres (or as a one-pixel spike when
narrower than half a pixel), so a line a few pixels wide changed height as it moved across the pixel
grid. Now each profile is averaged over each pixel (differences of erf at the pixel edges), lines
narrower than a pixel are widened in quadrature to one pixel, and the plot is binned at the device's
pixel resolution.

## Keeping zoom fast

Measured in headless Chrome over the DevTools protocol, a single zoom step takes 220–330 ms at any
width up to the full 270 000 lines, most of it the deliberate pause before the table is rebuilt.
What makes that possible:

- **Wheel events are coalesced.** A trackpad sends them far faster than a redraw; each one only
  moves the target view, and one redraw per animation frame catches up with the latest target.
- **The table waits for the wheel to stop** (160 ms); the spectrum redraws at once.
- **Wavelength order is free.** Shards are consecutive slices of one list sorted by wavenumber, so
  the lines in view are a bisected run of each, already in order, and the 500 shortest wavelengths
  are the end of that run. An earlier running-shortlist insertion sort was fine in wavenumber order
  but quadratic in the reverse, which is the default: 135 million comparisons per redraw of the full
  range. Other sort orders use a bounded heap, O(n log 500).
- **Decoded rows are kept per shard**, with each line's kind, so a zoom step builds no objects.
- **The three kinds of line are binned in one pass**, and colours are read from CSS once per draw
  rather than once per mark.

Wide views on a phone needed more. With the CPU throttled 4x in a 390 × 844 phone viewport, a zoom
step at the full range took about 2 s; it now redraws in 90–160 ms per frame:

- **Wide views are drawn from per-shard histograms.** Each shard's absorption is binned once per
  temperature and filter into 2 048 bins (about 0.08 cm⁻¹), each line split between its two nearest
  bins, and a view whose pixels are at least four histogram bins wide is resampled from them. Lines
  there are far narrower than a pixel, so the picture is the same; the work per frame no longer
  depends on the number of lines.
- **Counts and markers come from per-shard running totals.** The legend's counts are two subtractions
  per shard, and when there are more than 5 000 measured lines in view their markers come from a
  per-histogram-bin record instead of from the lines.
- **Line strengths are kept on each line** until the temperature changes.
- **The canvas uses at most 2 pixels per CSS pixel**, and is only resized when its size changes.
- **Zooming and panning preview on the compositor.** The plot is two canvases: the axes, grid and
  labels underneath, and the trace (fills, sticks, markers, selected line) on a layer clipped to the
  plot area. While a pinch, drag, wheel or key zoom or pan is in progress, every animation frame only sets a CSS
  `translateX · scaleX` on the trace layer that puts each wavenumber where it belongs in the new range,
  and redraws the axis labels. The browser composites that without redrawing a pixel. The proper redraw
  runs when the gesture pauses for 110 ms, and every 500 ms during a long one; the table waits until
  the gesture is over. Copying the canvas for the preview (`drawImage`) was tried first: reading pixels
  back from a canvas took 33 s of a 46 s profile.
- **Nothing waits for the network mid-gesture.** A redraw during a gesture uses the shards already
  loaded, fetches the others in the background and redraws when they arrive; once the view covers more
  than a fifth of the range, the rest of the list is fetched in the background too.
- Measured with the GPU on (a continuous two-finger pinch-out from 1 nm to the full range, 390 × 844
  viewport): every frame within 33 ms at full CPU speed; with the CPU slowed 4x, the median and 90th percentile
  17 ms, the 99th 83 ms, and 3 of 484 frames above 100 ms (the longest 233 ms), those being the
  periodic proper redraws.
- **Number formatters are reused**: `toLocaleString` builds a new one on every call, which was most
  of the cost of rendering the table.
